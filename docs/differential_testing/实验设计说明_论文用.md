# A2H 转换成功指标对比实验设计说明

本设计针对研究问题“翻译后不只长得像，还要功能像”。它依据《转换成功指标对比报告》第 7 节主结果表，并结合仓库已有的源端录制、目标端回放、L0-L2 状态预言、首分叉归因和修复回归链路。

## 1. 先修正第 7 节表格的比较对象

原表的列基本正确，但行混合了三种对象，直接填成一张大表会造成误读：

1. **同一基准上可重跑的方法/消融**：B0、compile-only、screenshot feedback、differential no repair、differential + repair、人工迁移上界。
2. **只在论文中报告过的外部靶子**：UITrans、GUIMigrator、Android→iOS Rule-Based 研究线索、LLMRR。除非拿到代码并在同一应用和同一协议下重跑，否则不能补齐本项目的功能列。
3. **测量模式而非完整翻译系统**：`LLMRR-style replay-only` 主要测控件匹配和脚本执行，不能被解释为目标应用功能等价。

因此论文应使用两张表：

- **主结果表**：只放在相同应用、场景、设备、轨迹和判定规则下实际重跑的条件；
- **文献对照表**：保留论文原始数字、原始分母、指标定义和可比性说明，缺失值写 `N/A`。

不能把 UITrans 的代码修改导向迁移成功率、GUIMigrator 的 SSIM 或 LLMRR 的脚本匹配率直接排成“功能优劣”名次。

## 2. 实验假设

- **H1：** 高视觉相似度不保证动态功能一致；存在 `Visual ≥ τv` 且 `R_eq_direct < τb` 的“长得像、功能不像”样本。
- **H2：** 逐步差分比只看编译、截图或脚本结束更早发现真实分叉，并能给出首分叉位置。
- **H3：** 差分证据驱动修复提高 `Scenario Pass` 和 `E2E-FP`，同时不会明显增加 `Regression Rate`。
- **H4：** 首分叉定位 F1 和修复成功率能解释“为什么通过/失败”，而不是只给一个最终成功率。

## 3. 主实验条件

| 条件 | 实验作用 | 是否执行功能差分 | 是否允许自动修复 |
|---|---|---:|---:|
| `B0` 原始翻译器 | 当前系统基线 | 是 | 否 |
| `compile_only` | 只用编译错误反馈的消融 | 是 | 只修编译错误 |
| `screenshot_feedback` | 只用视觉反馈的消融 | 是 | 只修视觉问题 |
| `replay_only` | 复现“动作能否执行”的基线 | 只记录回放 | 否 |
| `diff_no_repair` | 测试差分检测本身的价值 | 是，L0-L2 | 否 |
| `diff_repair` | 本文完整方法 | 是，L0-L2 | 是，按协议修复并回归 |
| `human_upper` | 同一任务的人工迁移参考上界 | 是 | 人工完成，不计自动修复 |

`UITrans`、`GUIMigrator`、`LLMRR` 只有在具备可运行实现且能接受同一输入时才加入上表；否则放入文献对照表，并保留其原始实验规模和分母。

## 4. 实验单位和控制变量

### 4.1 单位

- **应用**是工程单位，用于 Build/Deploy 和版本控制；
- **业务场景**是功能单位，用于完整场景通过率和 E2E-FP；
- **步骤**是诊断单位，用于 Step Replay、`R_eq_direct` 和首分叉；
- **修复缺陷**是修复单位，用于 Repair Success 和 Regression Rate。

每个应用准备 5–10 条确定性场景；每条场景 5–15 个事件，至少覆盖入口/主导航、核心功能和跨页面数据流。每个方法复用同一组安卓源端轨迹，不重新随机生成一组有利于自己的输入。

### 4.2 必须固定

固定源应用版本、目标代码版本、设备/模拟器、系统版本、屏幕尺寸和密度、语言时区、网络模式、数据初始化、页面对映射、文本掩码、平台差异白名单、等待稳定阈值和指标阈值。每条轨迹开始前清理目标端数据并冷启动。

网络或外部服务不能稳定复现时使用 mock；若无法观测某种副作用，报告 `N/A`，不要默认其一致。

## 5. 实验流程

### 阶段 0：冻结协议

冻结应用清单、场景清单、轨迹哈希、方法版本、设备配置和判定配置。先写入 `run_manifest.json`，再开始运行。

### 阶段 1：建立源端基线

在安卓源应用上录制或加载轨迹。每个事件保存目标控件指纹、执行前后 `StateVector`、截图和 dump。用源端自回放检查轨迹本身确定；不确定的轨迹标记 `INVALID`，不能进入目标端比较。

### 阶段 2：构建和部署

对每个方法记录构建尝试、编译错误、安装、启动和稳定首屏。构建或部署失败仍留在 E2E-FP 分母中；不能只统计“成功构建的子集”。

### 阶段 3：同轨迹目标端回放

目标端按抽象事件语义匹配控件并执行。每一步等待稳定，采集目标端状态并与安卓基线比较：

- L0：进程/页面仍存活；
- L1：页面或控件身份对应；
- L2：文本、输入值、开关、列表计数、选择项等语义状态一致；
- L3 视觉分数只作为辅助记录，不单独判定功能通过。

首次出现真实语义差异时记录首分叉并停止该轨迹，避免后续级联差异重复计数。

### 阶段 4：复现与归因

候选分叉在相同环境复跑 3 次。记录复现次数，并区分翻译缺陷、平台合法差异、源应用缺陷和环境噪声。只有经过复核的翻译缺陷进入 Repair Success 分母。

### 阶段 5：修复和回归

只对 `diff_repair` 执行证据驱动修复。每轮记录改动的翻译单元、构建结果、分叉变化和耗时，最多 3 轮；全部单元结束后对完整场景集全量回归。修复后当前场景通过但原来通过的场景失败，不算修复成功。

### 阶段 6：聚合和报告

先输出每条轨迹一行的明细，再从明细计算汇总。主表同时报告比例和 `通过数/总数`；成本报告墙钟时间、修复轮数、LLM 调用/token 和人工分钟数。

## 6. 指标和判定

| 指标 | 公式/判定 | 意义/功能 | 解释边界 |
|---|---|---|---|
| Build rate | 构建成功项目数 / 全部输入项目数 | 判断翻译产物能否通过编译，反映语法、类型和依赖处理是否基本可用 | 只说明工程可编译 |
| Deploy rate | 安装、启动、稳定首屏均通过的项目数 / 应部署项目数 | 判断产物能否真正安装并启动，为后续交互实验提供可运行入口 | 不能说明业务正确 |
| Visual | 预先声明的 SSIM（高好）或 LPIPS（低好） | 衡量目标界面在外观和结构上是否接近源界面，回答“长得像不像” | 只说明外观接近 |
| Step Replay | 成功匹配并执行的步骤 / 全部步骤 | 衡量目标端能否找到对应控件并完成动作，回答“动作能不能落地” | 不等于状态正确 |
| Complete Script | 执行到最后一步的脚本 / 全部脚本 | 衡量一条操作脚本能否连续跑完，反映长轨迹执行稳定性 | 不等于业务终态正确 |
| `R_eq_direct` | 未恢复且通过 L0-L2 的步骤 / 有明确结论的已执行步骤 | 衡量每个动作之后页面、控件和语义状态是否直接保持一致，是动态功能等价的核心步骤指标 | 必须与执行覆盖一起看 |
| Scenario Pass | 所有步骤、功能断言和终态检查通过的场景 / 有效场景 | 判断完整业务场景是否真正完成，回答“用户任务是否成功” | 一个关键步骤失败即失败 |
| E2E-FP | 同时通过构建、部署、回放、功能断言和回归的应用/场景 / 全部输入 | 汇总衡量从翻译产物生成到功能保持和回归稳定的端到端成功率 | 总体主指标 |
| First-div F1 | 系统首分叉与人工 ground truth 的 Precision/Recall/F1 | 衡量系统能否准确发现并定位第一次真实功能分叉，回答“错误从哪里开始” | 需要人工标注子集 |
| Repair Success | 修复后通过且全量回归无退化的缺陷 / 进入修复的已确认缺陷 | 衡量差分证据是否能转化为有效修复，且修复没有破坏已有功能 | 无修复条件为 N/A |
| Regression Rate | 修复后新失败的原通过轨迹 / 修复前原通过轨迹 | 衡量修复引入副作用的程度，检验功能改进是否以牺牲其他功能为代价 | 越低越好 |

视觉与功能的直接差距另报：`Visual ≥ τv` 且 `R_eq_direct < τb` 的场景数和比例。`τv`、`τb` 必须在正式测试前由验证集确定。

## 8. 文献对照表

外部靶子单独保存以下字段：方法、输入→输出、论文版本、应用/页面/脚本规模、原始指标、原始分母、是否可运行、与本实验的可比性、缺失项原因。

- UITrans：代码修改导向的迁移成功率，不能直接当作功能通过率；若本地重跑，再按主表口径补 Build/Deploy/Replay/状态指标。
- GUIMigrator：保留 migration completeness、SSIM、PSC 等原始值；与本项目的 `R_eq_direct`、Scenario Pass 并列解释，不互换。
- Android→iOS Rule-Based：作为规则映射研究线索；没有独立可核验数字时不填成功率。
- LLMRR：保留步骤匹配率和完整脚本率，但明确二者分母不同，并标记为 replay-only 证据。

## 9. 结果分析顺序

1. 先看 Build/Deploy，确认方法确实产生了可测试产物。
2. 再看 Step Replay 和 Complete Script，判断动作落地覆盖。
3. 以 `Scenario Pass` 和 E2E-FP 作为“功能像”的主结论。
4. 用 `R_eq_direct`、视觉—功能差距和首分叉步解释失败发生在哪里。
5. 对修复组同时看 Repair Success 和 Regression Rate；只报成功率不够。
6. 成本用墙钟时间、修复轮数、LLM 调用/token 和人工分钟数解释效率，不把不同计费口径合并成一个未经定义的数字。

## 10. 能写进论文的结论边界

可以声称：在相同输入和环境下，哪种方法提高了逐步状态一致率、完整场景通过率或端到端功能通过率；首分叉定位和修复回归是否有效；视觉相似与功能一致是否存在差距。

不能声称：UITrans 的迁移成功率高于/低于本项目的 Scenario Pass；GUIMigrator 的 SSIM 等于动态功能等价；LLMRR 的步骤匹配率等于业务场景通过率；或把论文没有报告的指标补成 0%。
