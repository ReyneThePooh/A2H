## 一、理论基础

### 1.1 测试预言问题（Test Oracle Problem）

任何测试都由两部分构成：**输入**（对 GUI 应用而言是一串用户操作）和**预言（oracle）**——即"判断程序对这个输入的反应是否正确"的判据。传统测试里预言是人写的断言（`assert result == 5`）。自动化 GUI 测试的根本困难是：机器可以自动生成成千上万条操作序列，却不知道"点了这个按钮之后界面**应该**长什么样"，所以绝大多数 GUI 模糊测试工具（Monkey、Fastbot 等）只能检测崩溃——因为"程序不应崩溃"是唯一不需要人工提供的预言。这就是文献中反复出现的 **oracle problem**（预言缺失问题）。

### 1.2 差分测试（Differential Testing）如何绕开预言问题

差分测试由 McKeeman 于 1998 年提出，核心思想：当你有**两个（或多个）声称功能等价的实现**时，不需要知道"正确答案是什么"，只需给它们**完全相同的输入**，然后**比较输出**。输出不一致就说明至少一个实现有错。编译器测试（CSmith、Rustlantis）、C→Rust 转译器测试（TOUCHSTONE、RustAssure）用的都是这套逻辑。

A2H 场景恰好满足差分测试的前提条件，而且比一般场景更强：

- 一般差分测试中两个实现不一致时，**不知道哪个错了**，需要引入第三方裁决；
- 而在"翻译评估"场景中，安卓原应用**按定义就是标准答案**（ground truth）——翻译的目标就是复刻它的行为。因此任何不一致，责任方默认是鸿蒙侧翻译产物（除非归因阶段排除，见 §4.8）。

形式化表述：设安卓应用为程序 P_A，翻译产物为 P_H，翻译系统的正确性要求是二者**行为等价**。对任意用户操作序列（称为一条**测试轨迹**，trace）t = ⟨e1, e2, …, en⟩，应有：

```
∀ i ∈ [1, n]:  α(S_A^i) ≡ α(S_H^i)
```

其中 S_A^i、S_H^i 是两端执行完第 i 个操作后的 GUI 状态，α 是**状态抽象函数**（把原始状态映射到"忽略平台无关紧要差异后的语义状态"，§2.4 详述），≡ 是在抽象域上的等价关系。测试的任务就是自动生成大量 t，寻找使等价关系被违反的反例；评估的任务是统计违反的频率、位置和类型。

### 1.3 为什么要加"模糊测试"（Fuzzing）

**模糊测试（fuzzing，模糊测试/随机测试）指自动、大量、带随机性地生成输入来测试程序的技术。** 名字里的"模糊"指输入不是人精心设计的，而是程序随机/半随机生成的——用廉价的数量弥补单条输入的针对性不足。这里它解决的是"输入从哪来"：人工写测试脚本成本高、覆盖有限；模糊生成可以廉价地产出成百上千条轨迹，把应用的页面和交互路径尽量遍历到。Monkey 就是最原始的 GUI 模糊器（每秒发送数百个随机坐标点击）。本设计用"**控件感知的模糊探索**"替代 Monkey——随机性保留，但每次随机选择的对象从"屏幕坐标"升级为"当前界面上真实存在的控件"（原因见 §2.1）。

## 二、核心概念精确定义

### 2.1 原生事件（native event）vs 抽象事件（abstract event）

**原生事件**是操作系统输入子系统真正接收的事件，绑定坐标和平台命令格式：

```bash
# 安卓：在屏幕坐标 (540, 1716) 处点击
adb shell input tap 540 1716

# 鸿蒙：同样是坐标点击，命令体系完全不同
hdc shell uitest uiInput click 540 1716
```

Monkey 发出的就是这种事件。它跨平台不可比的原因是：坐标 (540, 1716) 在安卓上落在"登录"按钮上，但翻译后的鸿蒙应用因为布局引擎（ArkUI 的 Flex 布局 vs 安卓的 ConstraintLayout）、屏幕密度、系统状态栏高度不同，同一坐标可能落在空白处或别的控件上。**给两端发"相同坐标"实际上是发了"不同输入"，差分测试"相同输入"的前提直接被破坏。**

**抽象事件**是本设计引入的平台无关表示：不描述"点哪个坐标"，而描述"**对哪个语义控件做什么动作**"。例如：

```json
{
  "step": 7,
  "action": "CLICK",
  "target": {
    "role": "button",
    "text": "登录",
    "id_hint": "btn_login",
    "content_desc": null,
    "rel_bounds": [0.08, 0.86, 0.92, 0.93],
    "screenshot_patch": "traces/t013/step7_target.png"
  },
  "params": {}
}
```

字段含义：`action` 是动作类型（词表见下）；`target` 是目标控件的**多重指纹**——资源 ID、可见文本、无障碍描述、控件角色、**相对边界**（`rel_bounds`，控件边框占屏幕的比例坐标，消除分辨率差异）、目标控件的小截图。之所以存多个指纹，是因为翻译后任何单一字段都可能变（ID 可能没被保留、文本可能措辞微调），匹配时需要多证据投票（§4.5）。

动作词表（覆盖绝大多数移动应用交互）：

| 抽象动作 | 参数 | 安卓落地 | 鸿蒙落地 |
|---|---|---|---|
| `CLICK(w)` / `LONG_CLICK(w)` | 目标控件 | uiautomator2 `.click()` | hmdriver2 `.click()` / `uitest uiInput` |
| `TYPE(w, text)` | 控件+文本 | `.set_text()` | `.input_text()` |
| `SWIPE(dir, dist)` | 方向、距离比例 | `input swipe` | `uitest uiInput swipe` |
| `BACK` / `HOME` | — | `input keyevent 4` | `uitest uiInput keyEvent Back` |
| `ROTATE(orient)` | 横/竖屏 | `settings put` | hdc 显示设置 |
| `WAIT_IDLE(timeout)` | 超时 | 见 §4.6 稳定判据 | 同左 |

### 2.2 抽象事件是怎么来的（关键机制：执行—提炼—再落地）

**抽象事件不是凭空先生成再分发到两端的**——凭空生成不可行，因为"哪些操作合法"取决于当前屏幕上有什么控件，而这只有运行时才知道（比如"登录"按钮只在登录页存在）。正确的机制是三步：

**第一步：在源端（安卓）具体执行。** 探索器连着真实运行的安卓应用，每一步先读取当前屏幕的控件清单（读取方式见 §2.3 的 dump），从"当前可交互控件"里选一个（选法见 §4.2），用原生命令执行。此时事件天然合法——它操作的是屏幕上真实存在的控件。

**第二步：提炼（lifting，提升/抽象化）。** 执行的瞬间，把"我刚才对哪个控件做了什么"记录成上面的 JSON：从控件树节点里抠出 ID、文本、类型、相对位置，截下控件小图。原生事件 `input tap 540 1716` 被提升为 `CLICK(text="登录", id="btn_login", ...)`。一条轨迹跑完，就得到一个抽象事件序列文件。

**第三步：在目标端（鸿蒙）再落地（grounding，具体化）。** 回放时逐条读取抽象事件，在鸿蒙当前屏幕的控件清单里**搜索**与指纹最匹配的控件（§4.5 的对齐算法），找到后换算出它在鸿蒙屏幕上的真实坐标/对象句柄，用鸿蒙原生命令执行。

所以准确地说，这套方案是"**源端录制驱动的跨平台差分回放**"：安卓端是"边模糊探索边录制"，鸿蒙端是"语义回放"。Monkey 的角色被替换为第一步里的控件感知探索器，但"自动随机生成大量输入"的模糊测试本质没变。

另有一条辅助来源：对登录、下单等**必经流程**，允许人工用同一 JSON 格式手写少量**种子脚本**（seed，作为轨迹前缀），模糊探索接在种子之后继续随机走。这解决纯随机过不了登录页的问题（Kea2 的"脚本引导 fuzzing"就是这个思路）。

### 2.3 dump 是什么：控件树的获取

**控件树**（widget tree / view hierarchy，视图层级）是 GUI 界面的结构化表示：一棵树，每个节点对应屏幕上一个 UI 元素，带属性（类型、文本、边界框、能否点击等）。**dump**（导出/转储）指通过系统提供的无障碍或测试接口，把当前屏幕这棵树完整导出成 XML/JSON 文件的操作——它是运行时读取"屏幕上有什么"的标准手段，两个系统都有官方支持：

安卓（UIAutomator 框架，`adb shell uiautomator dump` 或 uiautomator2 库）导出 XML：

```xml
<node class="android.widget.Button"
      resource-id="com.example.app:id/btn_login"
      text="登录" content-desc=""
      bounds="[84,1650][996,1782]"
      clickable="true" enabled="true"/>
```

鸿蒙（uitest 框架，`hdc shell uitest dumpLayout`，或 Python 库 hmdriver2）导出 JSON：

```json
{"attributes": {"type": "Button", "id": "btn_login",
                "text": "登录", "bounds": "[84,1520][996,1652]",
                "clickable": "true", "enabled": "true"},
 "children": []}
```

两种格式字段名和树结构不同，因此需要一个**归一化层**：把两端 dump 都转换为统一 schema（字段：`role / id / text / desc / abs_bounds / rel_bounds / clickable / editable / checked / children`）。这一步有现成先例——华东师大的 HMDroidbot 工具内部就把鸿蒙 uitest 的布局 JSON 转成了 Droidbot 的安卓风格树。归一化之后，"对齐""比较"两个模块面对的是同构数据，不再关心平台差异。

**dump 在整个系统里出现在三个位置，作用不同**：① 源端探索时 dump，用于枚举"当前能点什么"（输入生成）；② 目标端回放时 dump，用于搜索匹配控件（事件落地）；③ 每步执行完两端各 dump 一次，用于状态比较（预言检查）。同一份 dump 可以复用于 ② 和 ③。

### 2.4 GUI 状态与状态抽象函数 α

**原始状态**指某一时刻能观测到的一切：控件树、截图、前台页面名、系统日志、应用私有存储。直接比较原始状态必然误报——两端字体渲染、状态栏时钟、动画帧都不同。所以定义**状态抽象函数** α：从原始状态中抽取一个**语义状态向量**，只保留"用户关心的信息"：

```
α(S) = ( page, T, W, V, crash )
```

- **page**：页面身份。安卓取当前 Activity 类名（`dumpsys activity top`），鸿蒙取当前 Ability/页面路由名。两者名字不同，通过**页面对（page pair）映射表**关联——该表可在首次遍历时用"页面指纹"（标题文本 + 控件统计特征）自动建立；
- **T**：屏幕上全部**可见文本的多重集合**（multiset，考虑重复次数的集合），并做掩码处理：剔除时间、日期、验证码等易变串（正则识别）；
- **W**：**可交互控件摘要**——各角色（按钮/输入框/开关/列表项）的数量与文本标签集合；
- **V**：**关键值状态**——每个输入框的当前内容、每个开关的选中态、列表的条目数；
- **crash**：进程是否存活、日志中是否出现崩溃签名（安卓 logcat 的 `FATAL EXCEPTION`；鸿蒙 hilog/faultlogger 的 `cppcrash`/`jscrash`/`appfreeze`）。

**等价判定 ≡ 不是布尔而是分层的**，详见 §4.7。设计原则：**结构和语义信号为主，像素信号只作辅助**——这是 SetDroid、Genie、VisionDroid 等工作反复验证过的经验，像素级比较在跨设备场景假阳性率过高。

### 2.5 轨迹、分叉、首个分叉点

- **轨迹（trace）**：一次完整测试运行产生的抽象事件序列 t = ⟨e1, …, en⟩，连同每步之后两端的状态记录。
- **分叉（divergence，行为分歧）**：回放过程中第一次出现以下两种情况之一的步骤 i：
  - **执行分叉**：ei 在鸿蒙端落地失败——对齐算法在鸿蒙控件树中找不到置信度达标的匹配控件（该按钮没被翻译出来、被遮挡、或页面早已走错）；
  - **状态分叉**：ei 两端都执行成功，但 α(S_A^i) ≢ α(S_H^i)（比如安卓跳到了详情页、鸿蒙留在原页；或安卓列表新增一条、鸿蒙没有）。
- **为什么每步都比、发现分叉就停止，而不是把 n 个事件跑完只比终态**：GUI 是**有状态**系统，第 i 步的语义依赖第 i−1 步之后所处的界面。一旦第 i 步已分叉，两端从此处于不同页面，后续事件 e(i+1) … en 在鸿蒙端会作用在错误的界面上，产生的所有后续差异都是第 i 步差异的**级联放大**，不携带新信息，反而会把一处翻译缺陷统计成几十处。逐步比较保证每条轨迹**恰好归责到一个缺陷点**——这就是"首个分叉点"（first divergence point）的意义：它是缺陷定位坐标。
- **停止该轨迹时记录什么**：分叉步号 i、分叉类型（执行/状态，及违反的预言层级）、事件 ei 全文、两端在第 i−1 和 i 步的 dump 文件与截图、两端日志片段。这一个包就是一份可复现的缺陷报告。
- 停止后该轨迹作废尾部，测试框架回到初始状态（清应用数据、重启应用）开始下一条轨迹。**变体**：如果目标是"一条轨迹里找尽可能多的缺陷"而非精确打分，可以尝试**重同步**（resynchronization）——跳过分叉步，检查后续某步两端页面身份是否重新一致，一致则继续；但重同步会污染完成度指标的统计口径，评估用途下建议默认关闭。

## 三、完整链路总体流程

```
┌─────────────────────────────────────────────────────────────────┐
│ 阶段0  环境控制：双端设备就绪、确定性配置、网络mock、数据清零        │
└──────────────────────────────┬──────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段1  源端探索+录制（安卓）                                       │
│   循环: dump控件树 → 枚举可交互控件 → 策略选控件+动作               │
│         → 原生执行 → 提炼为抽象事件 → 记录状态                     │
│   产出: 抽象事件轨迹库 {t1, t2, ...}（含每步安卓状态基线）           │
└──────────────────────────────┬──────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段2  目标端语义回放（鸿蒙），对每条轨迹逐事件:                     │
│   dump鸿蒙控件树 → 归一化 → 控件对齐(级联匹配)                     │
│     ├─ 匹配失败 → 记录执行分叉，终止本轨迹                          │
│     └─ 匹配成功 → 鸿蒙原生执行 → 等待界面稳定                       │
│         → 两端状态抽象 α → 分层预言比较                            │
│             ├─ 等价     → 下一事件                                │
│             └─ 不等价   → 记录状态分叉，终止本轨迹                  │
└──────────────────────────────┬──────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段3  去噪与归因: 分叉复跑n次 → 稳定复现才保留                     │
│        → 分类{翻译缺陷 | 平台固有差异 | 源应用bug | 环境噪声}        │
└──────────────────────────────┬──────────────────────────────────┘
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ 阶段4  度量聚合: 可回放率 / 状态一致率 / 分叉深度分布                │
│        / 页面覆盖对齐率 / 控件召回率 → 翻译完成度报告               │
└─────────────────────────────────────────────────────────────────┘
```

**用一个实例把链路走一遍**（登录场景）：

1. 阶段 1，安卓端：探索器 dump 出登录页控件树，发现可交互控件 {用户名输入框, 密码输入框, 登录按钮, 忘记密码链接}。策略选中输入框，执行 `TYPE(用户名框, "user01")`，提炼记录；再选密码框输入；第三步选中登录按钮 `CLICK`。执行后 dump 显示 Activity 从 `LoginActivity` 变为 `MainActivity`，屏幕文本出现"欢迎, user01"。这三个抽象事件加三份安卓状态存入轨迹 t013。
2. 阶段 2，鸿蒙端：装好翻译产物、清数据启动。回放 t013 第 1 条：dump 鸿蒙登录页，归一化，对齐器拿"用户名输入框"的指纹（id_hint=`et_username`、role=textfield、rel_bounds≈屏幕上 1/3 处）在鸿蒙树中打分搜索，命中鸿蒙的 `TextInput` 组件（id 保留、位置相近，得分 0.91 > 阈值 0.75），用 hmdriver2 输入文本。第 2、3 条同理。执行完第 3 条，等待稳定后两端取 α：安卓 page=`MainActivity`，鸿蒙 page=`MainAbility`（页面对映射表中已关联），文本集合都含"欢迎, user01"，L0–L2 全部通过 → 本步等价，轨迹继续。
3. 假如翻译器漏译了登录按钮的点击回调：第 3 条事件鸿蒙端能找到按钮、点击也成功，但页面不跳转。状态比较发现 page 不对（鸿蒙仍在登录页）→ **状态分叉，步号 3，违反 L1**，打包两端截图与 dump，终止 t013，报告"登录按钮交互逻辑未翻译"。
4. 阶段 3：该分叉复跑 3 次全部复现，且不属于权限弹窗等平台差异白名单 → 判定为翻译缺陷。
5. 阶段 4：t013 计入统计——回放率 3/3，一致率 2/3，首分叉深度 3。

## 四、逐模块详细设计

### 4.1 环境控制器

差分测试的有效性取决于"除被测差异外，其余变量全部对齐"。具体控制清单：

- **设备**：安卓模拟器/真机 + 鸿蒙模拟器（DevEco Studio 提供）/真机，分辨率与 DPI 尽量选相近档位；
- **确定性配置**：两端统一系统语言、时区、字号缩放；关闭动画（安卓 `settings put global animator_duration_scale 0`，鸿蒙关闭动效开关）；固定系统时间或在文本掩码中剔除时间；
- **网络**：三选一——完全离线应用直接测；有网络的应用用**录制回放代理**（如 mitmproxy：先在安卓端跑一遍录下所有 HTTP 响应，鸿蒙端回放同样的响应），保证两端看到相同服务端数据；或搭桩服务器（stub server）返回固定数据；
- **初始状态归零**：每条轨迹前清空应用私有数据（安卓 `pm clear`，鸿蒙 `bm clean --data`），保证轨迹间独立、可复现。

### 4.2 事件生成器（源端探索策略）

三档，按投入递增：

1. **纯随机（Monkey 档）**：仅作 baseline 对照组，预期结论是"坐标事件跨端不可比、覆盖浅"，用于论文中证明控件感知的必要性。
2. **控件感知随机探索**（默认档）：每步从 dump 出的可交互控件中加权随机选择。权重设计：未点过的控件优先（新颖性）、`EditText` 类控件配语料库文本（合法邮箱/超长串/emoji/SQL 特殊字符，体现 fuzz 的边界试探）、以小概率插入 `BACK`/`ROTATE` 等系统事件。同时维护 **UTG**（UI Transition Graph，界面跳转图：节点=去重后的界面状态，边=触发跳转的事件），用于引导探索器走向未覆盖页面——这是 DroidBot/Fastbot/HMDroidbot 的成熟做法。
3. **种子引导探索**：人工种子脚本走完登录等关卡后接随机探索；进阶可用 LLM 按业务场景引导（ScenGen、HACMony 的做法），提高深层页面覆盖。

### 4.3 事件抽象器

录制时对每个执行的事件生成 §2.1 的 JSON。两个细节：

- **指纹要在执行前采集**（执行后界面可能已跳转，目标控件已不存在）；
- 每步同时记录 `pre_state_hash` / `post_state_hash`（安卓端 α 向量的哈希），回放端用 `pre_state_hash` 做前置校验：若鸿蒙当前状态与安卓录制时的前置状态早已不匹配，说明上一步其实已经分叉，避免把错误归到本步。

### 4.4 跨端适配器

两个薄封装，接口一致（`dump() → 归一化树`、`execute(抽象事件, 匹配到的节点)`、`observe() → 原始状态`）：

- **安卓适配器**：uiautomator2（Python，支持控件对象操作、dump、截图）+ adb（logcat、`dumpsys activity`、`pm clear`）；
- **鸿蒙适配器**：hmdriver2 或 hdc 原生命令（`uitest dumpLayout` 取树、`uitest uiInput` 注入事件、`uitest screenCap` 截图、hilog 取日志、`bm clean` 清数据）。

这两套工具链都已被公开项目验证可用（uiautomator2 生态成熟；鸿蒙侧 HMDroidbot、hmdriver2、Kea 均在真实鸿蒙 NEXT 设备上跑通）。

### 4.5 控件对齐器（整个方案的技术核心）

输入：抽象事件的目标指纹 f、鸿蒙归一化控件树的候选节点集 C（按动作过滤，如 CLICK 只考虑 `clickable=true` 的节点）。对每个候选 c 计算加权相似度：

```
score(c) = w1·sim_id + w2·sim_text + w3·sim_role + w4·sim_pos + w5·sim_img
```

- **sim_id**：资源 ID 字符串相似度（若翻译器保留了 ID 命名，这一项几乎是决定性的；权重最高）；
- **sim_text**：可见文本/无障碍描述的编辑距离相似度；
- **sim_role**：控件角色是否同类（按钮↔Button、输入框↔TextInput，维护一张安卓类名→鸿蒙组件类型的角色映射表）；
- **sim_pos**：`rel_bounds` 的中心点距离与面积比（相对坐标，天然抗分辨率差异）；
- **sim_img**：录制时的控件小截图与候选控件区域截图的感知哈希/嵌入相似度（LIRAT 验证过的手段，对图标类无文本控件重要）。

判定规则：取最高分 c*。若 score(c*) ≥ θ_hi（如 0.75）且与第二名差距明显 → 匹配成功；若 θ_lo ≤ score < θ_hi 或前两名接近 → 标记 `AMBIGUOUS`（歧义），可选调用多模态 LLM 仲裁（LLMRR 的三级策略：图像匹配→文本匹配→LLM 语义匹配，其在 iOS/安卓/鸿蒙 20 个应用上验证了该级联的有效性）；若 score < θ_lo → `UNMAPPED`（无对应控件）。

注意 `UNMAPPED` **本身就是评估信号**而非测试失败：它直接对应"该控件未被翻译或不可交互"，计入控件召回率指标。

**多对多映射的处理**：跨端交互并非总是一对一（LLMRR 明确报告了此现象，如安卓一个对话框对应鸿蒙两步操作）。工程上的收口：为已知的系统级模式（权限弹窗、日期选择器、返回手势）维护**模式适配规则表**，一条抽象事件可展开为目标端的短事件序列；规则表外的多对多场景计入 `PLATFORM_ONLY` 并从等价性统计中剔除，避免误判。

### 4.6 界面稳定判据（何时才能 dump 来比较）

事件执行后界面有过渡期（页面切换动画、网络加载、进度条）。过早 dump 会把"还没加载完"误判为分叉。稳定判据：轮询 dump，连续两次控件树哈希相同且间隔 ≥ 500ms 视为稳定；上限超时（如 10s）仍在变化则标记 `UNSTABLE` 并用最后一帧参与比较（同时记录标志，供归因阶段降低该步置信度）。安卓端另可用 uiautomator 的 `waitForIdle`。两端各自等稳定后再进入比较，两端等待时长不要求一致。

### 4.7 分层预言（oracle）与比较谓词

从"必须成立"到"仅供参考"排列，逐层短路（上层失败即报分叉，不再看下层）：

- **L0 存活性**：鸿蒙进程存活、无崩溃签名、前台仍是被测应用。安卓正常而鸿蒙违反 → 最严重的翻译缺陷（崩溃类）。两端同时崩 → 归为源应用缺陷，不计翻译扣分。
- **L1 页面身份**：查页面对映射表，判断两端是否处于对应页面。违反 → 导航逻辑翻译错误（跳错页/没跳转）。
- **L2 语义内容**（核心层，在 L1 通过、即同页的前提下比）：
  - 掩码后可见文本多重集合的 Jaccard 相似度 ≥ 阈值（如 0.9）：J = |T_A ∩ T_H| / |T_A ∪ T_H|；
  - 可交互控件对齐率：安卓端各控件能在鸿蒙端找到匹配的比例 ≥ 阈值；
  - 值状态逐项相等：输入框内容、开关选中态、列表条目数。
  - 违反 → 内容/状态类翻译缺陷（丢控件、丢数据、状态没同步）。
- **L3 视觉参考**（不作为分叉依据，只随报告输出）：掩码系统栏后的截图 SSIM（结构相似性指数，一种衡量两图结构接近程度的经典指标，取值 0–1）或感知哈希距离，供人工审查布局观感；如需自动化的视觉判断，可用多模态 LLM 对两张截图做"是否同一功能界面"的判定（VisionDroid 路线），但其输出应视为带噪标注。
- **L4 副作用**（可选扩展）：比较应用私有存储的关键键值（安卓 SharedPreferences ↔ 鸿蒙 Preferences）、导出文件、发出的网络请求序列（经 mock 代理天然可得）。覆盖"界面看着一样但后台逻辑错了"的深层缺陷，对应 Odin/Genie 关注的非崩溃逻辑错误。

### 4.8 去噪与归因

每个候选分叉进入四分类，只有第一类计入翻译质量扣分：

1. **翻译缺陷**：确定性复现（复跑 ≥3 次全现），且不匹配平台差异白名单 → 按违反层级细分为崩溃/导航/内容/状态四型；
2. **平台固有差异**：命中白名单（权限弹窗时机、系统字体度量、返回手势语义、鸿蒙特有系统 UI）→ 剔除；白名单由预实验人工构建并随案例增长；
3. **源应用缺陷**：两端同现异常，或安卓端自身复跑不稳定 → 剔除；
4. **环境噪声**：复跑不能复现（网络抖动、时序竞态）→ 剔除，并反馈到 §4.1 收紧控制。

自动化优先用规则（崩溃签名、白名单正则），残余交人工或 LLM 辅助标注；论文中应抽样人工核验并报告分叉判定的精确率。

### 4.9 度量体系

对轨迹库 {t1, …, tm}，设 |tk| 为轨迹长度，dk 为首分叉步号（无分叉则 dk = |tk|+1）：

- **事件可回放率** R_replay = Σk(dk − 1) / Σk|tk|：鸿蒙端成功走完的事件占比（执行层完成度）；
- **状态一致率** R_eq：所有已执行步中通过 L0–L2 的比例（行为层完成度）；
- **轨迹通过率**：完整无分叉走完的轨迹比例（端到端完成度）；
- **归一化首分叉深度** avg(dk/|tk|)：越大说明浅层交互越可靠；
- **页面覆盖对齐率**：安卓探索触达的页面中，鸿蒙存在对应页面且可到达的比例（页面级翻译完成度）；
- **控件召回率**：所有被操作的安卓控件中对齐成功（非 UNMAPPED）的比例（组件级完成度）；
- **缺陷谱**：四型翻译缺陷的计数与分布。

这组指标与 UITrans 的"组件/页面/工程编译成功率"正交互补：他们度量**静态可构建性**，这里度量**动态行为保持性**——后者才对应"翻译出来的应用能不能用"。

## 五、可行性论证与已知边界

| 模块 | 需要成立的命题 | 已验证的证据 |
|---|---|---|
| 鸿蒙事件注入/树 dump | 鸿蒙端可编程测试 | hdc uitest / Hypium 官方支持；hmdriver2、HMDroidbot（开源，鸿蒙 NEXT 实测）|
| 控件感知探索 | 自动生成合法 GUI 输入 | Monkey→DroidBot→Fastbot2（ICSE-SEIP 2022，字节量产）→HMDroidbot（鸿蒙版）|
| 跨端控件对齐 | 语义级匹配跨 OS 可行 | LIRAT（ICSE 2021，图像+布局）、MAPIT（ASE 2021，双向迁移）、LLMRR（软件学报 2025，**含鸿蒙**，三级级联匹配）|
| 双端并行差分 + GUI 预言 | 双设备逐步比较架构可运转 | DiffDroid（ASE 2017）、SetDroid（ISSTA 2021/TSE 2023，双设备+一致性预言，产业部署）、Odin（FSE 2022，深状态差分）|
| 非崩溃逻辑缺陷检测 | 语义状态比较能抓真 bug | Genie（OOPSLA 2021）、Kea（ASE 2024）/Kea2（2025，进华为 DevEco AppAnalyzer）|
| "翻译产物 vs 原程序"差分 | 方法论正当性 | 转译器差分测试全谱系：TOUCHSTONE（2023）、Rustlantis（OOPSLA 2024）、RustAssure（arXiv 2025）、PROGnosticator（FSE 2026）|

结论：**没有任何一个环节需要发明全新技术**；创新点在于组合与问题定位——把转译器差分测试的方法论第一次落到"跨 OS GUI 应用翻译"上，并把差分结果结构化为翻译完成度度量。风险最高的环节是控件对齐（对齐错误会同时造成假阳性和假阴性），因此论文实验必须单独报告对齐器的准确率（可人工标注若干控件对做 ground truth）。

已知边界，写作时应作为 limitation 主动声明：深层业务路径覆盖依赖种子质量；富动画/游戏类界面不适用（控件树无语义）；平台差异白名单有人工成本；两端模拟器性能差异要求稳定判据保守设置。

## 六、轻量化环内测试详细设计（嵌入 A2H 迭代循环）

### 6.1 为什么需要两个版本

完整链路（第三、四章）里真正"重"的是三块：**模糊探索**（要跑几千个事件才能积累覆盖）、**大规模轨迹库回放**（小时级）、**去噪归因**（要复跑、要人工核验）。这些是"系统性评估"的成本，放进翻译迭代循环里意味着每改一个 Unit 就要等几小时——不可接受。

但反过来，迭代循环需要的不是"全面体检"，而是"**这轮改动有没有把功能改对/改坏**"的快速信号。这在软件工程里对应两个成熟概念：

- **冒烟测试（smoke test）**：用最少量的关键用例快速验证"基本功能还活着"，名字来自硬件测试"通电后先看冒不冒烟"；
- **回归测试（regression test）**：每次修改后重跑一组固定用例，确认旧功能没被改坏；
- **质量门禁（quality gate）**：CI/CD 流水线里的检查点，不通过就不允许进入下一阶段。

轻量版差分测试 = 把完整版的"回放 + 比较"内核抽出来，按冒烟/回归测试的规模运行，充当 A2H 迭代循环的功能质量门禁。**代码上两版共享同一批模块**（适配器、归一化、对齐器、预言），轻量版只是换了输入来源（固定种子轨迹而非 fuzz 生成）并关掉部分预言层。

### 6.2 术语回顾（本章自足所需）

- **fuzz / 模糊测试**：自动、大量、带随机性地生成测试输入的技术（详见 §1.3）。**轻量版恰恰把 fuzz 砍掉了**——环内不随机生成新输入，只回放固定的种子轨迹。理由：随机输入每轮不同，会导致"这轮报错、下轮不报"的不稳定信号，修复环节无法跟进；固定输入保证每轮迭代面对同一张考卷，进步可度量。fuzz 留给环外完整版做最终评估。
- **dump / 控件树导出**：通过系统测试接口把当前屏幕的 UI 元素树导出为结构化文件的操作（详见 §2.3）。轻量版每个回放步骤仍然要 dump 两次用途：在鸿蒙树中找目标控件（对齐）、执行后取两端状态（比较）。
- **种子轨迹（seed trace）**：预先录制、内容固定的抽象事件序列，作为回放的"考题"。"种子"一词沿用 fuzzing 术语：完整版里它是随机探索的起点（种子会被延伸变异），轻量版里它就是全部输入（不延伸）。
- **增量测试（incremental testing）**：只重跑与本次代码改动相关的用例，跳过无关用例，以缩短反馈时间。

### 6.3 裁剪原则：砍什么、留什么、为什么

| 完整版组件 | 轻量版处置 | 理由 |
|---|---|---|
| 控件感知模糊探索（阶段1） | **砍**，换成固定种子轨迹 | 环内要的是稳定回归信号，不是覆盖扩张；随机性破坏轮间可比性 |
| 大轨迹库（数百条） | **砍**，5–10 条种子 | 分钟级预算；关键流程足以暴露"功能不像" |
| 逐事件对齐+执行+比较（阶段2内核） | **全保留** | 这就是功能验证本体 |
| 预言 L0/L1/L2 | **保留** | 崩溃、跳错页、丢内容正是"功能不像"的三种表现 |
| 预言 L3 视觉 / L4 副作用 | **砍** | L3 假阳性高且"看起来像"已不是问题；L4 实现重 |
| 去噪归因四分类（阶段3） | **砍**，只保留"复跑 1 次确认" | 环内默认全算翻译问题交给修复；修不动的再人工看 |
| 度量聚合（阶段4） | **简化**为单轮通过/失败 + 一致率 | 门禁只需要布尔决策与趋势曲线 |
| 环境控制（阶段0） | **保留**（数据清零、动画关闭、mock） | 成本低，且是信号稳定的前提 |

### 6.4 种子轨迹：录制、格式、维护

**录制（一次性，安卓端）**：对每个被测应用，用"人工操作 + 自动记录"的方式产生种子——测试者在安卓设备上手动走一遍关键流程（登录 → 浏览列表 → 打开详情 → 修改数据 → 返回），录制器在后台对每次操作执行 §2.2 的提炼，同时记录每步的安卓状态基线 α(S_A)。5–10 条轨迹、每条 5–15 个事件，人工成本约半小时/应用。

**选择标准**：优先覆盖①应用入口与主导航（最常用路径）；②每个核心 CRUD 功能各一条（增删改查）；③至少一条跨页面数据流（在 A 页输入、在 B 页看到结果——最容易暴露状态同步类翻译缺陷）。

**格式**：与完整版完全相同的轨迹 JSON（§2.1 事件 schema + 每步状态基线），因此环外完整版可以直接复用种子做 fuzz 起点。

**维护**：种子录制自安卓原应用，而原应用在整个 A2H 迭代期间不变，**所以种子全程不需要重录**。只有当换了被测应用、或发现种子覆盖不到某类高频缺陷时才补录。

### 6.5 增量回放选择策略

A2H 流水线本身有"Unit（翻译单元）→ 源文件 → 页面"的对应关系（翻译计划里已有 Unit 与 Activity/布局文件的绑定）。据此建立两张映射：

1. **Unit → 页面集合**：该 Unit 包含或引用的 Activity/布局对应的页面；
2. **轨迹 → 页面序列**：每条种子轨迹录制时记录了逐步的 page 字段，天然构成它途经的页面列表。

每轮迭代改动了 Unit 集合 U，则本轮需要回放的轨迹为：**途经页面与 U 的页面集合有交集的全部种子轨迹**。保守起见，若映射缺失或 U 涉及全局文件（Application 类、公共工具），则全量回放（反正上限只有 5–10 条）。

### 6.6 环内预言子集与判定协议

每个回放步骤依次检查（任一失败即分叉、终止该轨迹，进入 §6.7 报告）：

1. **对齐检查**：目标控件在鸿蒙树中匹配得分 ≥ θ_hi？失败类型 = `对齐失败`（控件未译出/不可交互）；
2. **L0 存活**：进程活着、无崩溃签名、前台是被测应用？失败类型 = `崩溃`；
3. **L1 页面**：两端页面身份对应（查页面对映射表，环内可先用"录制时的 page 序列"做期望值——鸿蒙端页面应与安卓基线序列同步推进）？失败类型 = `跳错页`；
4. **L2 语义**：掩码文本 Jaccard ≥ 0.9、值状态逐项相等？失败类型 = `丢内容/状态漂移`。

**单轮判定**：本轮选中的所有轨迹全部走完且无分叉 → **通过**（该 Unit 的行为等价获得确认，迭代进入下一 Unit）；任一轨迹分叉 → **失败**，输出分叉报告。分叉后建议立即在鸿蒙端复跑该轨迹 1 次：复现 → 确认报告；不复现 → 标记 `FLAKY`（不稳定），本轮放行但计入观察名单（连续两轮 FLAKY 升级为失败）。

### 6.7 分叉报告作为修复输入

报告直接面向修复环节（LLM 或人工），一个分叉一份，字段设计为"修复所需的最小充分信息"：

```json
{
  "trace_id": "seed_03_登录后修改昵称",
  "diverged_step": 5,
  "failure_type": "L2_丢内容",
  "abstract_event": { "action": "CLICK", "target": { "text": "保存", "id_hint": "btn_save" } },
  "expected": { "page": "ProfileActivity", "must_contain_text": ["昵称已更新"], "list_count": null },
  "actual":   { "page": "ProfileAbility", "missing_text": ["昵称已更新"] },
  "suspect_units": ["Unit_Profile"],
  "artifacts": {
    "android_screenshot": "…/step5_android.png",
    "harmony_screenshot": "…/step5_harmony.png",
    "harmony_dump": "…/step5_harmony.json",
    "harmony_log_tail": "…/step5_hilog.txt"
  }
}
```

`suspect_units` 由分叉页面反查 §6.5 的映射得到，让修复环节直接定位到要改的翻译单元；`expected` 来自录制时的安卓状态基线，天然是"正确答案"。

### 6.8 迭代协议与退出条件

- 每个 Unit 的"翻译 → 编译 → 轻量差分"最多重试 N 轮（建议 N=3）：N 轮内通过 → 前进；N 轮仍分叉 → 挂起该缺陷、标记人工介入，迭代继续处理其他 Unit（避免死循环卡住全局）；
- 全部 Unit 完成后，跑一次**全量种子回放**（所有轨迹，不做增量过滤）作为出厂检查——增量策略可能漏掉跨 Unit 的耦合缺陷；
- 环外完整版（fuzz + 全预言 + 归因 + 指标）只在实验评估阶段运行，不参与迭代。

### 6.9 单轮开销预算分析

单个回放步骤的耗时构成：鸿蒙 dump（约 0.5–1s）+ 对齐计算（纯本地计算，<0.1s，不调用 LLM 时）+ 事件执行（<0.5s）+ 稳定等待（0.5–3s）+ 比较（<0.1s），合计约 2–5s/步。一条 10 步轨迹约 30–60s（含启动与清数据）；一轮增量选中 2–3 条轨迹时**总耗时 2–5 分钟**，与一次 hvigor 编译构建同量级，满足"环内"要求。加速手段：轨迹间不重启模拟器只清应用数据；多条轨迹在多个模拟器实例上并行。

### 6.10 轻量版实例走查

设本轮迭代修复了 `Unit_Profile`（个人资料页）。① 由映射查得途经 Profile 页的种子轨迹有 seed_03（登录后修改昵称）与 seed_07（查看资料页）；② 部署新 HAP、清数据；③ 回放 seed_03：前 4 步（登录、进资料页、输入新昵称）逐步等价；第 5 步点击"保存"后，安卓基线显示应出现文本"昵称已更新"，鸿蒙端 dump 中该文本缺失 → L2 分叉；④ 复跑 1 次仍复现 → 生成 §6.7 报告（failure_type=丢内容，suspect_units=[Unit_Profile]）回灌修复环节；⑤ 修复环节根据报告重译保存回调，下一轮 seed_03 全通过、seed_07 也通过 → 该 Unit 门禁放行。

## 七、论文定位建议

主角是翻译系统，差分测试是仪器。写作时把它收敛为"功能一致性反馈机制 + 评估方法"一节，不展开成第二篇测试方法学论文（完整的 fuzz 驱动评估可留作 future work 或独立成文）。贡献清单：

1. 指出并量化"视觉像、功能不像"的评估缺口（用完整版跑 baseline 产物：L3 视觉一致率高、L2 行为一致率低的对比表）；
2. 提出以跨端差分回放为反馈信号的迭代翻译框架（轻量版）；
3. 行为等价性指标下的实证提升（完整版对比"无功能反馈 baseline" vs "差分反馈迭代后"）。

实验建议：对象为本流水线译出的应用 + UITrans 译出产物 + 少量人工迁移应用（upper bound）；消融含"坐标回放 vs 语义对齐回放""逐步同步 vs 盲回放""有无分叉反馈"；人工标注部分分叉核验精确率/召回率；主动讨论威胁（非确定性、平台设计差异、覆盖深度、对齐误差）。
